# PresenceAI

React/Vite/Tailwind frontend with Supabase Auth and PostgreSQL for business onboarding and prompt/scan records. Signup includes a 6-digit verification screen. Onboarding now asks one question at a time, reviews business details and Brand Truth, and creates a verified business through the existing APIs.

## Run locally

Redesign Phase 3 adds the translucent business wizard and interactive dot background. Add business opens `?view=onboarding`; incomplete business profiles can resume setup. Official name/website and served city are prefilled, optional facts can be skipped, and final owner confirmation is required. Unsaved answers are kept for this account in this tab; they are not synced across devices. Final save creates the business and a verified truth revision. Stable creation IDs and revision checks make retries safe after a lost response. Drafts clear after completion/logout or confirmed session expiry. Temporary authentication/network failures preserve drafts; saving also checks that the signed-in account still matches the draft owner. Completed setup links reopen the saved success screen after refresh. Lint/build and 25 tests pass; browser flow and retry tests use isolated mock data, with no hosted test business created. A shared glass panel is used throughout the new profile and remains the design direction for later dashboard phases.

Requires Node >=24.12.0. Run `npm ci`, then copy `.env.example` to `.env.local` and set the project's **publishable** Supabase API key. The URL is already set to project `nougnhpinewhbgixjwgc`. Run `npm run dev` and open http://localhost:5173. Auth, business onboarding, and prompt management work without a local backend; live scans require the separate worker below.

The current Supabase project has the Phase 1 schema applied from `supabase/migrations/20260928153921_presenceai_phase1.sql`. Its Auth Site URL is `http://localhost:5173/`, with `http://localhost:5173/?view=dashboard` allowed for confirmation redirects. For another deployment, set its own site URL and exact redirect URL in Supabase Auth settings. Hosted Supabase normally requires email confirmation before the first sign-in; the UI explains this after signup.

Never put a Supabase secret or service-role key in `VITE_` variables. The publishable key is intentionally browser-visible. PostgreSQL grants and Row Level Security restrict businesses and verified Brand Truth to their owner. No AI-generated content writes to Brand Truth.

## Phase 2 prompts and scans

The sidebar contains Business profile, Prompts, Analytics, Fix queue (disabled), and Scan history. Select an owned business using the switcher, or open one from the All businesses list. Existing create/delete and verified Brand Truth flows remain accessible. The four sample-data analytical tabs are removed from navigation; their source components remain for reference. Dashboard and onboarding now require a real signed-in session.

Open **Business profile** for business details, grouped owner-verified facts, and the latest finished scan's saved-answer count, **unprompted brand-name mentions**, cited-answer count, summary excerpt, and three recent scan links. A pending/running scan has separate progress and never replaces the finished snapshot with zeros. The Analytics overview retains category coverage and the full combined analysis. The mention count includes only saved answers to questions that did not name the business; it matches the full name or an inferred location-free form when the saved name ends in its city or country. A text match does not mean the model recommends it. Use **Manage prompts** to review questions, **View analytics** for the overview, or **View this scan** for that exact historical board. Step 1 generates 20 unbranded customer-discovery questions from the business category and location, such as “What are the best furniture stores near me in Hyderabad?” and “Where can I find affordable, good-quality furniture in Hyderabad?” The generator removes business-name terms from the category and does not include Brand Truth facts in its questions. You can fill a short list to 20, edit/exclude/delete questions, add custom prompts, or confirm replacement of an existing set with 20 discovery questions. Existing prompts are not rewritten automatically. The prompt set persists; a scan snapshots the exact active questions so later edits or replacement never change historical evidence.

The scan migrations create `prompts`, `scans`, `prompt_runs`, `raw_responses`, `scan_analyses`, `business_measurement_config`, and `scan_measurements`. Owners manage prompts and their reviewed tracking names, and read their scan evidence and scores through RLS. Only the server-side worker writes scans, raw responses, analyses, and saved measurements. The Phase 6B migration is `supabase/migrations/20261012171902_versioned_scan_measurements.sql` and is applied to the connected Supabase project.

For live scans, put `SUPABASE_SECRET_KEY` and `GEMINI_API_KEY` in ignored `.env.scan`, then run `npm run dev:scans` alongside `npm run dev`. Optionally set `GEMINI_MODEL`; it defaults to `gemini-3.5-flash-lite`. `GEMINI_REQUEST_INTERVAL_MS` defaults to 6000 to pace a multi-prompt run; the worker also backs off and retries once after a 429 rate-limit response. Google returned a 404 for `gemini-2.5-flash-lite` on a new key and recommended this newer model. A Gemini API key works across models available to its Google AI Studio project; the model is selected by this worker, not encoded in the key. The scan server listens on `127.0.0.1:3002` and Vite proxies `/scan-api` to it. `SUPABASE_SECRET_KEY` is the project's server-only Supabase secret key. **Never put either secret in a `VITE_` variable or commit `.env.scan`.** Without the keys, prompt management still works, but the scan server reports that live scans are unavailable. An old `OPENAI_API_KEY` or `OPENAI_MODEL` entry is ignored.

The worker processes queued scans outside the browser, retries a failed prompt once, continues after individual failures, stores the full provider payload and exact answer before marking a run successful, and recovers interrupted jobs through leases. After saving individual answers, it asks the same Gemini model for a combined summary and themes with prompt-number evidence, then stores both the report and its raw Gemini payload. A separate leased extraction job uses saved answers and the scan-time truth/identity snapshot to produce quoted evidence and deterministic metrics. Extraction failure preserves raw answers and a retry resumes without new customer-answer calls. The discovery scan input does not include verified Brand Truth. On 2026-10-05, a full 20-prompt scan of the placeholder `Testname` business completed through the dashboard: 20/20 answers and raw responses saved, zero failed, combined analysis succeeded, and the dashboard's eight exact-name text matches and zero cited answers matched SQL. That older scan predates Phase 6B and is intentionally unscored. A reviewed real-business persisted scan and production deployment remain unverified. Issue generation and report export remain future work. Google's free-tier Gemini API inputs and outputs may be used to improve its products; check the current [Gemini pricing and data-use terms](https://ai.google.dev/gemini-api/docs/pricing) before scanning sensitive information.

All calls succeeded, but none had provider web citations. Official pages exposed a wrong precise IKEA address and several missed current policies in the first run; the combined reports summarized answers without verifying truth. ## Scope and local data

Implemented: signup with 6-digit OTP verification, login/logout, a persisted one-question onboarding wizard, owned business creation/deletion, versioned and explicitly verified Brand Truth, unbranded discovery-prompt generation with persistent prompt CRUD, scan evidence storage, a saved combined Gemini summary, reviewed tracking names, and versioned model-assisted mention/recommendation/truth-agreement and competitor metrics for new scans. Redesign Phase 1 adds shared light/dark themes and query navigation (`business`, `section`, optional `scan` and `mode`) with refresh/Back support. Account identity is read-only; the preferred display name is explicitly saved in this browser only. The legacy sample analytical tabs are outside navigation. The metrics are within-prompt-sample measures, not independently established factual accuracy or market share. Issue generation and report export remain planned.

The earlier Node/SQLite Phase 1 prototype is still available when the Supabase variables are absent. Its ignored database at `data/presence.sqlite` is preserved. SQLite accounts and passwords are **not** Supabase accounts. To use the connected site, create a Supabase account and verify its email; old local business records are not automatically transferred between identities. The legacy API can be started with `npm run dev:server` only when using the SQLite fallback.

Run `npm run lint`, `npm test`, and `npm run build`. On Windows environments that block child processes, `node --test --test-isolation=none server/*.test.js` runs the same test files without spawning test workers. See [the repository audit and implementation order](docs/AUDIT.md).

## Deployment

Set `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` during the build and add the deployed site's HTTPS URL to Supabase Auth's redirect allowlist. Deploy the scan server separately with its server-only credentials and background worker process. The current configuration is for local development.
